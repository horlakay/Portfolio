I Built a Cloud-Native Fraud Detection Platform, Then Rebuilt the Path to the Product When the Cloud Failed Me

SentinelStream started as a serious systems-design challenge and became something more: a working analyst platform, a local fallback deployment path, and a Windows desktop artifact that proved the project could survive beyond ideal cloud assumptions.

Why this page exists

This is a public, Medium-inspired archive for one of the most important engineering milestones in the SentinelStream journey. It captures not just what was built, but what had to be solved to make the system resilient, demonstrable, and product-shaped.

FastAPI Python Kafka / Redpanda Postgres Redis Terraform Helm Electron

Some projects start because you want to learn a new framework. SentinelStream started because I wanted to build something that forced me to think like a systems engineer, a platform builder, and a product owner at the same time.

Fraud detection is one of those domains that refuses to stay simple. It is part security problem, part data problem, part systems problem, and part human-decision problem. You are not just classifying events. You are ingesting activity, enriching it, running rules, layering machine learning, producing a decision, making it explainable, and then handing it to a person who still needs to trust what the system is doing.

That was the pull for me. I did not want to build a notebook demo and pretend it was a platform. I wanted something more credible: modular services, event-driven flow, observability, deployment realism, and an analyst-facing product surface.

“I did not want to prove that I could write a single service. I wanted to prove that I could build the path from ingestion to analyst review.”

What SentinelStream Actually Is

At a plain-English level, SentinelStream is a cloud-native fraud detection and analyst decision-support platform. It takes incoming transactional or event data, enriches it, scores it, checks it against explicit rules, makes a final decision, stores the result, and then exposes that result to a human analyst through a review console.

Under the hood, the system is split into Python microservices: ingestion-service, feature-service, rule-engine, model-service, decision-service, feedback-service, and analyst-console.

The flow is intentionally modular. The ingestion layer receives activity and publishes it into the pipeline. The feature layer derives context. The rules layer brings deterministic fraud logic. The model layer provides machine-learning inference. The decision layer combines those pieces into an outcome. The feedback layer captures analyst review. And the analyst console turns the whole thing into something usable by a human, not just a service mesh.

Supporting that pipeline are Postgres for persistence, Redis for caching, and Kafka-compatible messaging through Redpanda. Just as importantly, observability was treated as part of the architecture instead of an afterthought: structured logs, traces, metrics, and OpenTelemetry were all included because I wanted a system that could actually be understood when it failed.

Why the Architecture Matters

I chose microservices because the components in a fraud system do not evolve at the same pace. Rules change differently from model logic. Analyst workflows change differently from ingestion logic. Keeping those concerns separated makes experimentation, debugging, and future scaling much more practical.

I chose an event-driven pattern because fraud and risk workflows are rarely just clean request-response interactions. They are streams, state transitions, dependencies, and downstream actions. Messaging made it easier to reflect that reality instead of flattening the system into synchronous calls only.

I also made a deliberate architecture decision not to choose between rules and machine learning. In real fraud operations, explicit rules still matter. They are fast, understandable, and often operationally important. Machine learning expands the system with pattern recognition that rules alone will miss. The real system value came from letting both exist in one pipeline.

And above all of that sits the analyst. That part mattered to me. If the system produced decisions but gave no meaningful review path to a human operator, it would still be incomplete.

The Hard Engineering Reality

SentinelStream did not move from architecture sketch to stable deployment in a straight line. That is part of why this milestone means so much to me: it required real debugging, not just clean implementation.

The infrastructure path included Terraform, ECR, EKS, Helm, GitHub Actions, and Kubernetes. That meant the challenge was not just “does this code run?” but “does the whole environment behave the way this system assumes?”

Some of the fixes were small on paper but important in practice: Terraform ECR output fixes, ECR lifecycle policy corrections, cheaper and more realistic dev node choices, model-bootstrap workflow fixes, Helm annotation typing fixes, service exposure changes for the analyst console, and far better deployment diagnostics when things failed.

Then came the deeper work. Services were crash-looping. Dependency timing became very real. I had to trace Postgres connectivity from environment configuration into async SQLAlchemy and asyncpg to prove the actual runtime hostname path. I had to untangle Kafka warnings from the true startup failure. I had to treat lifecycle cleanup as a real engineering concern, because failing startup without graceful shutdown creates its own confusion.

The ugly part of distributed systems is not that they fail. It is that they often fail noisily enough to hide the first real cause if you have not built the right diagnostics.

When the Cloud Path Broke

The biggest disruption in the project was not a syntax error. It was infrastructure reality. The AWS path was serious: Terraform, EKS design, Helm deployment, CI/CD, containerized services. But at a critical point, the AWS account became suspended. That meant the intended cloud deployment path stopped being the reliable route for showing the platform.

That kind of event can make a project feel like it has hit a wall. It can turn months of work into a deployment footnote.

Instead, it forced a much better engineering response: stop treating the original infrastructure plan as the only valid finish line.

The Pivot That Saved SentinelStream

The best product decision in this milestone was the pivot to a local fallback deployment path.

Rather than abandon the cloud-native architecture, I adapted it for local reproducibility. I reused the existing Helm chart and Kubernetes structure, stabilized the demo-data stack around Postgres, Redis, and Redpanda, and made local image build and load flows much more practical.

That work changed the project in an important way. SentinelStream stopped being a platform that only looked complete when the ideal cloud environment was available. It became a platform that could preserve the user outcome even when the original path was blocked.

That is a lesson I will not forget: resilient product thinking does not end at service design. It includes delivery paths, demo paths, and fallback paths too.

The Desktop App Milestone

Once the local platform path became stable enough, the next question changed from “can this run?” to “can this feel like a product?”

That is what pushed me to package the analyst console into a Windows desktop shell using Electron.

This shifted SentinelStream from being only a backend platform into something more product-shaped. The desktop work introduced a Windows installer, a portable executable, embedded and external launch modes, persisted settings, startup and fallback screens, and the first serious Microsoft Store-readiness planning materials.

It also surfaced a new category of engineering reality. Packaging is not the same thing as programming. Build artifacts can collide. Packaged binaries do not always behave like local source runs. Embedded-mode assumptions that work in development can fail after packaging. Product polish lives in those details.

Solving those issues mattered because it moved the project one step closer to something I could point to not just as an architecture, but as a product artifact.

What I Learned

SentinelStream taught me that architecture is only impressive if it survives contact with operations. A clean diagram is not enough. A real system needs startup discipline, dependency realism, observability, cleanup behavior, and fallback thinking.

It also reinforced how important observability is. Logs, traces, health checks, and diagnostics are what turn failure into learning. They are what separate “something is broken” from “I can explain what is broken and why.”

The project also taught me the difference between code completion and product completion. The services working together was an important milestone. The analyst console becoming usable was another. The desktop shell becoming launchable and packageable was yet another. Those are not the same thing, and each one matters.

Key Takeaways

  • Serious systems become real when architecture, operations, and usability meet.
  • Rules, machine learning, and analyst oversight are stronger together than in isolation.
  • Cloud-native systems benefit from local fallback paths, not just cloud-first plans.
  • Startup order, lifecycle cleanup, and diagnostics are core distributed-systems skills.
  • Productization begins when the system becomes usable, not just deployable.

Why This Milestone Matters to Me

There are projects you finish and move on from quickly. Then there are projects that change the way you think. SentinelStream is one of those for me.

It forced me to work across architecture, microservices, event-driven design, infrastructure as code, Kubernetes, deployment, CI/CD, debugging, observability, desktop packaging, and release thinking. It pushed me past the point where “the code works” was enough.

That is why I wanted to archive this milestone properly. Not just because the platform exists, but because the journey taught me how to keep building when the cleanest path failed. It taught me how to preserve the user outcome, not just the original plan.

SentinelStream now exists not only as a set of services, but as a platform with an architecture, a fallback story, a desktop artifact, and a path toward something that feels increasingly like a product.
